# ReadRay 性能优化流程

> 改编自 [Emanuele-web04/skills – optimize-codebase-performance.md](https://github.com/Emanuele-web04/skills/blob/main/skills/optimize-codebase-performance.md)（MIT，2026-08-07 安装）。
> 改编要点：删除纯服务器/容器基础设置；git 只读状态检查、不做变更；LLM 请求不重复统计；基准测试在优化前先确认基线。

**name:** optimize-codebase-performance

**description:** 对 ReadRay 执行有边界、以证据驱动的性能优化：建立可复现基线、按层定位瓶颈、小批量修改后重新测量，输出带百分比变化的 before/after 基准。适用于减少 CPU/RAM/GPU/延迟/IO/渲染/成本或缩短启动时间的请求；要求先测量、后修改、用数据收尾。

---

把性能工作当作持续工程循环：先建立可信基线，找到被测量的瓶颈，做小而安全的改动，用同一工作负载重新测量，在证据表明目标已达成或继续投入不再划算时停止。

## 操作契约

- 扮演高级性能工程师，独立完成调查、实现、验证和最终基准报告。
- 显式使用用户要求的目标：CPU、RAM、GPU、延迟、I/O、渲染、成本或组合。**不要优化未测量的代理指标。**
- 循环受 TODO/目标计划、可用预算、正确性和明确的停止条件约束。绝不运行无界或字面意义上的无限循环。
- **Git 纪律**：优化运行期间不做任何变更类 git 操作（不 commit、不 push、不 checkout、不 stash）。只允许 `git status` / `git diff` 只读检查来确认工作区边界。文件系统、测试和基准产物才是真相源。
- 把子代理当作审计员：它们可以检查代码、profile 和基准结果并返回发现，但**不得修改文件**。
- 只对非显而易见的点做外部研究。优先版本匹配的官方文档和定向 web search；记录来源并验证建议适用后再改代码。
- 保持改动本地化、可逆。优化改变语义时保持行为并补测试。
- 涉及基础设施、购买、权限变更、外部写入或把敏感项目数据发给第三方服务前先征求同意。
- 请求"检查/诊断/计划"时只报告发现不改代码；请求"优化"时做范围内的本地改动并跑非破坏性验证。

## 工作流

### 1. 范围与基线

建立 TODO/目标计划，包含检查点：

1. 范围、环境、目标指标、工作负载、成功标准。
2. 基线测量与可复现命令。
3. 分层瓶颈分析。
4. 候选改动、风险、预期指标影响。
5. 实现与正确性检查。
6. 独立审计与重新测量。
7. 最终基准与交接。

重大工具调用前先说明决策和理由。检查点前先确认优化点确实存在（见"已知基线"）。

按 ReadRay 的恢复流程开始：先读 `AGENTS.md` → `docs/RESOURCE_MAP.yml` → 按资源地图决定后续读取 → 若涉及方向/架构/路线再读 `docs/DEVELOPMENT_PLAN.md` → 涉及继续开发或恢复上下文再读 `docs/HANDOFF.md`。**默认不全量扫描仓库。**

先记录相关环境（Windows 版本、Node/pnpm/Rust 工具链、Tauri 版本、Rust 依赖、构建配置）再编辑。建立代表性工作负载，并按层捕获：

- **CPU**：墙钟时间、平均/峰值利用率、热点函数、线程/worker 行为。
- **RAM**：常驻/集合大小、峰值分配、分配率、保留对象、缓存增长。
- **GPU**：利用率、显存、着色器热点、传输/拷贝开销。
- **服务行为**：延迟百分位、吞吐、队列深度、I/O、错误、成本。
- **UI**：渲染时间、布局/绘制时间、帧率、组件渲染频率、网络与图片成本。

保存足够多的原始证据以复现基线。**没有配对的同工作负载基线+改动后测量，不得声称任何百分比提升。**

### 2. 分析所有相关层

只选项目里存在的层，不强行分析不存在的层：

- **应用**：算法、重复工作、分配、拷贝、同步、并发、批处理、序列化、日志、资源生命周期、错误路径。ReadRay 重点：Rust 侧（`src-tauri/src/`）与前端（`src/`）分开分析。
- **依赖与库**：版本特定热路径、默认值、传递成本、构建 flag、原生绑定、更安全低成本的替代。改动依赖前先说明必要性、替代方案、打包影响。
- **桌面/原生层（Tauri 特有）**：窗口创建/隐藏/恢复、全局快捷键、托盘、UIA 捕获、单实例、启动流程、IPC channel 开销。
- **SQLite**：查询计划、缺失索引、逐行读取、WAL/日志模式、迁移成本、每次调用新建连接 vs 复用。
- **UI 与设计组件**：对每个有意义的组件检查不必要渲染、昂贵 effect、布局抖动、未虚拟化大列表、图片解码、动画工作、冗余请求。浏览/模拟器仅当可用且任务在范围内时使用。
- **数据与工作负载形状**：峰值来自输入大小、并发、冷启动、缓存状态还是特定请求路径。

对每个疑似热点说明证据、机制、拟改动、预期权衡、可证伪该假设的测量。优先用最小改动验证假设。

**本机环境**：涉及验证命令、环境异常时采用 `docs/WINDOWS_ENVIRONMENT.md` 的既有基线：Node `D:\Application\nvm\nodejs\node.exe`、pnpm `D:\Application\nvm\nodejs\pnpm.cmd`（版本 10.30.3）、Git HTTPS remote（`http.sslBackend=schannel`）、Vite 端口 1420。启动 `pnpm tauri dev` 前先检查 ReadRay 进程和 1420 端口；发现已有实例先判断能否复用。

### 3. 按测量批次实现

只归组密切相关的改动。每个批次：

1. 说明假设与预期指标变化。
2. 做最小范围内本地编辑。
3. 跑针对性正确性检查（含测试），再跑代表性基准。
4. 与基线及紧邻前一版本比较。
5. 正确性失败、目标指标明显变差或引入不合理权衡时回退或修改。
6. 用证据更新 TODO/目标与下一步决策。

> 不要从研究或审计报告生搬硬套建议。**不优化未在测量路径上的代码**，除非是合理证明过的预防性修复。

**验证基线（ReadRay 专属）**，按 `docs/WINDOWS_ENVIRONMENT.md` 与测试脚本：

- 前端测试：`pnpm test:conversation`、`pnpm test:writing`、`pnpm test:settings`（Node 内置 test runner，无新增测试依赖）。
- 构建：`pnpm build`（tsc + vite build）。
- Rust：`cargo fmt --check`、`cargo check --manifest-path src-tauri/Cargo.toml`、`cargo test`（含 `--ignored` 的真实 DeepSeek live 测试仅按既有标记跳过）。
- 其他：RESOURCE_MAP YAML 解析、`git diff --check`。
- 性能相关优化必须附带配对的测量证据；未验证的风险必须说明。

**已知基线**：以下领域已完成优化或边界明确，**不应作为优化的出发点**（除非有新的实测证据推翻）：

- 流式渲染：`finish_reason=length` 截断、`text-wrap: pretty` 移除、滚动距底部 <80px 才跟随 —— 200 词段落生成从约 1 分钟降至约 16 秒（2026-08-07，任务 2）。
- 窗口交互：位置方案已接受，不再重复校准默认位置（`HANDOFF.md`"当前已知限制与后续边界"）。
- `QUICK_AI_MAX_TOKENS` 已 2048 → 8192（DeepSeek 文档上限）。
- 系统提示词已重构为分节构建；诚实边界明确（无网络/无工具/无本地记忆）。**不得为性能优化破坏诚实边界。**

**有效优化目标**（按项目历史与当前风险）：前端大列表虚拟化、SQLite 连接复用与查询计划、Tauri 冷启动/窗口恢复延迟、流式长对话渲染、无边框透明窗口 resize 命中区、内存占用（随包 34MB 字体是内容资源，不是优化目标）、打包体积。

### 4. 审计与研究

每个有意义的批次后，若有子代理则做独立审计。给审计员相关文件、profile 和基准输出，请它们寻找遗漏热点、回归、测量缺陷和不安全假设。不给他们编辑权限。

本地证据有缺口时才做定向外部研究（如框架默认值、allocator 行为、Tauri/WebView2 设置、部署限制）。记录 URL、适用版本、建议与为何适合此工作负载。研究保持只读，不暴露私有代码或凭据（含 DeepSeek Key）。

若可选的第二意见工具（如 `claudex`）可用且用户授权，只把它当作额外审计员。它的输出只是仍需本地测量的假设。

### 5. 主动停止

满足以下任一条件即停止：

- 目标与正确性标准达成且基准可复现。
- 后续迭代收益递减或不一致。
- 剩余瓶颈需要范围外的架构、基础设施或产品决策。
- 改动带来的风险/成本/延迟/复杂度超过测得的收益。
- 时间、计算或工具预算耗尽。

停止时，只有成功标准已验证才标记目标达成；否则报告剩余阻塞、证据和最小的下一步实验。

## 基准与交接

- 工作量、环境、命令、样本数、预热策略、方差。
- 每个目标指标的基线值与优化后值。
- 绝对差值及百分比减少/增加。
- 每个重要改动的函数/库/组件/基础设施设置。
- 正确性/测试状态、回归、权衡、限制与建议下一步。

对越低越好的指标：`减少百分比 = (基线 - 优化后) / 基线 × 100`。
吞吐提升单独报告为增加，不叫减少。保留负面结果——它们防止重复劳动并使优化决策可审计。

若任务有交接价值，按 `AGENTS.md` 与 `HANDOFF.md` 规则更新交接记录。

## 提示与响应纪律

- 保持指令精简：每条规则只说一次，只暴露相关工具，只保留编码了真实需求或修复过已测可靠性缺口的示例。
- 前置定义角色、目标、约束、证据要求、成功标准、输出格式。
- 最终响应先说结果。保留决策、证据、重要注意事项和下一步；去掉重复与套话。
- 重复基准字段用表格，解释用简洁段落。使用项目既有格式约定。

## 基准准则

在验证或交接时使用此参考。协议足够短以便重复，足够严格以便比较有意义。

### 测量协议

记录：

- 目标指标及越低/越高越好。
- 确切工作负载、输入形状、并发、缓存状态。
- 影响结果的硬件、OS、运行时、框架、依赖、构建、部署设置。
- 所用命令/脚本、预热策略、样本数、顺序或并发。
- 均值/中位数与 p95/p99 或峰值，加方差或置信区间。
- 无关负载、节流、后台服务、已知混淆因素。

基线与优化后测量用同一协议。重复有噪声的工作负载直到方向与量级稳定到足以支撑决策。条件变化时把比较标注为方向性而非因果性。

### 报告表格

每个重要优化一行：

| 层 | 热点/改动 | 工作负载 | 基线 | 优化后 | 绝对差 | % 减少/增加 | 证据 | 权衡 |
|---|---|---|---|---|---|---|---|---|
| 应用/依赖/桌面/UI | 函数/库/组件/设置 | 可复现用例 | 值+单位 | 值+单位 | 优化后-基线 | 下方公式 | profile/追踪/测试/基准 | 内存/延迟/成本/复杂度/无 |

越低越好：`减少 % = (基线 - 优化后) / 基线 × 100`
越高越好：单独报告 `增加 % = (优化后 - 基线) / 基线 × 100`

### 验收清单

- 每个声称的改动都有同工作负载的配对测量。
- 指标方向与单位明确。
- 正确性测试与行为检查通过。
- 目标为资源稳定性或延迟时，检查了峰值与尾部行为。
- 包含回归与负面结果。
- 外部建议已链接且版本匹配。
- 说明剩余瓶颈与下一个最小实验。
